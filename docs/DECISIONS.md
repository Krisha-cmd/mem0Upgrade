# Decisions log

Every place where the build prompt was wrong about an external fact, was silent, or conflicted
with itself. Format: **ID: decision.** *Why.* Status. Dates are when the decision was made.

## Facts that differed from the prompt (followed the source)

- **D-001: PrefEval has 1,000 explicit preference–question pairs, not about 3,000** (20 topics, 31–62 per topic). *Checked at commit `50795054`. "About 3,000" counts 1,000 pairs × 3 forms (explicit, choice-based, persona-driven); the implicit files reuse the same 1,000 pairs.* 2026-11-21.
- **D-002: The main E2 set is 1,000 positive + 250 null at N=25, not 1,500 + 375.** *Each target can be used only once (section 13 forbids sampling targets with replacement), and only 1,000 targets exist. The null share stays at exactly 20%. As a result, E2's instance set is the same as E1's N=25 set (`prefeval_multi_N25.jsonl`). E3 keeps 500 + 125 per N, stratified by topic (`*_sub500.jsonl`).* 2026-11-21.
- **D-003: Every PrefEval topic has fewer than 75 items, so null-query selection always samples with replacement** (section 13 rule). Targets never do. 2026-11-21.
- **D-004: PrefEval's judge returns XML (`<explanation>`/`<preference>` + `<answer>`), not JSON.** *The prompt asks for a "fixed output schema (JSON)", but it also asks for the judge prompts to be reproduced faithfully. Faithfulness wins: the 4 prompts and the system prompt are copied verbatim (`src/scopemem/prompts/judge_prefeval/`), and the parser is strict on the XML tags, with one re-ask on a parse failure. The original judge was Claude-3-Sonnet on Bedrock with max_tokens=100; we use the local judge with max_tokens=256.* 2026-11-21.
- **D-005: GPU stack pinned to `vllm==0.11.0` + `torch==2.8.0` (CUDA 12.8 wheels), `transformers==4.57.1`, `sentence-transformers==5.1.2`, `mem0ai==2.2.1`.** *Driver 570.158.01 supports CUDA ≤ 12.8. vLLM ≥ 0.20 requires torch ≥ 2.11, whose default PyPI wheels target CUDA 13. `slurm/check_debug.sbatch` prints `torch.version.cuda` to confirm 12.8 on the cluster.* Verify at first cluster run.
- **D-007: The full model set is about 180 GB of safetensors, above the 150 GB budget** (Qwen-32B 65 GB, the two 70B-class AWQ models about 40 GB each). *`download_models.py` downloads in groups: `core` (about 63 GB) first, then `llama8b`, `qwen32b` and `judge2` only when their experiments run. Delete groups that are no longer needed to stay under the 300 GB `$HOME` quota.* 2026-11-21.
- **D-008: The second judge is `casperhansen/llama-3.3-70b-instruct-awq`, a community AWQ quantisation.** *Meta publishes no official AWQ release of Llama-3.3-70B-Instruct (the official model is 141 GB in bf16).* 2026-11-21.
- **D-019: Mem0 (`mem0ai==2.2.1`) config keys verified from source.** The keys are: provider `vllm` (`model`, `vllm_base_url`), embedder `huggingface`, vector store `qdrant` with local `path`. `Memory.search` defaults to `threshold=0.1`, so we pass 0.0 for a pure top-k. Mem0 sends **posthog telemetry by default**, so `MEM0_TELEMETRY=False` is set in every job. 2026-11-21.
- **D-023: PrefEval has 11 duplicated preference texts (988 unique).** The distractor pool is de-duplicated by text, so a user never holds the same preference twice. 2026-11-21.
- **D-027: Other datasets.** PersonaMem is at HF `bowen-upenn/PersonaMem-v1` (MIT), pinned at revision `a8076d56`. v2 and v3 have since been released, but we use v1 as in the paper, with the 32k split by default. LoCoMo is at `snap-research/locomo` `data/locomo10.json` (10 conversations, 1,986 QA). Category 5 (adversarial) is excluded, which I believe matches the Mem0 protocol. *Verify against Mem0's evaluation code in Phase 7.*

## Defaults chosen where the prompt was silent

- **D-006: Core dependencies use version ranges in `pyproject.toml`. Exact versions are frozen to `results/env/pip_freeze.txt` and `conda_env.yml` at the first cluster run.** *vLLM's own pins (numpy, pydantic, etc.) must win on the cluster. Hard-pinning laptop versions would make the env unsolvable.*
- **D-009: A global preference replaces one distractor, so |P| = N.** It is added only when N ≥ 2, only to positive users, with p = 0.3 per user, and it goes into G.
- **D-010: Null instances never get a global preference, so G = ∅ strictly.** *Otherwise "null" would not measure over-application.*
- **D-011: History construction.** After each preference turn, the assistant reply is a fixed acknowledgement ("Got it, I'll keep that in mind."). PrefEval instead generates a model reply. *A fixed reply is deterministic, costs nothing and is the same for every backbone.* PrefEval's suffix "(Please respond within N words.)" is **not** appended to queries, because it would interact with the global length preference. Filler is sampled **per exchange** from the 316 filler exchanges, without replacement within a user while possible (100 × 3 = 300 ≤ 316).
- **D-012: `pref_tokens` = tokens(prompt with memory block) − tokens(same prompt without it)**, using the backbone tokenizer with the chat template, so template overhead is attributed exactly. For B1, `pref_tokens` = the history's tokens.
- **D-013: The memory block is appended to the system message** (`<fixed system>\n\nUser preferences:\n- ...`). It is omitted when empty.
- **D-014: `write_tokens_amortised` = the user's scope-writer tokens / 100 queries.** `write_tokens_user` is also stored, so E6 computes C(Q) = W + Q·R exactly for any Q.
- **D-015: The scope JSON may be wrapped in a ```json fence. Any other surrounding text makes it invalid** (re-ask once, then fall back). Prompts carry a version tag (`[prompt-id: SCOPE_WRITER_V1]`). Scope writer: temperature 0, max_tokens 256. B5 selector: max_tokens 64.
- **D-016: Tuning objective = micro-F1 pooled over dev instances**, so null instances contribute their false positives. τ candidates are 101 quantiles of the dev scores. Ties go to fewer selections (higher τ, lower k). The k grid is {1, 2, 3, 5, 7, 10}.
- **D-017: S3 training pairs are built from PrefEval items in the training topics.** Negatives come only from other *training* topics. *This avoids same-topic false negatives and any test-topic scopes in training.* Global preferences are added as extra positives with p = 0.3.
- **D-018: S3 is trained with a plain torch loop** (1 epoch, BCE-with-logits, lr 2e-5, batch size 32) over the HF model inside the sentence-transformers CrossEncoder, so it is robust to ST API changes. **Caveat:** per section 6.4, S3's τ is tuned on the same 4 folds it was trained on, which may make τ optimistic. If dev F1 for S3 is much higher than its held-out F1, switch to an inner split (flag for Phase 5).
- **D-020: `always_on` comes from the scope writer's flag, not from gold.** Always-on preferences are added *outside* the k_max cap. The cap applies to threshold-selected preferences, sorted by score.
- **D-021: Cross-encoder scores = sigmoid(raw logit).** Raw logits are requested explicitly, because ST's default activation would otherwise apply a second sigmoid.
- **D-022: No query instruction prefix for bge embedders.** *The query is matched symmetrically against example requests and scope sentences.*
- **D-024: The construction is nested across N.** Draws are seeded per instance, not per N, so P at N=5 ⊂ P at N=10 for the same instance. *This gives paired comparisons across N in E3.* The target's position in H is random (shuffle).
- **D-026: The local profile tunes on the 200-instance subset. The cluster tunes on the full instance file.**
- **D-029: Raw file names.** Retrieval cells are `<cond>/shard_N<N>.jsonl`. Generation shards are `<cond>/N<N>_shard_<i>.jsonl`. *E3 has several N per condition directory, so N must be in the file name.*
- **D-030 (open): For E8 implicit forms, what goes into the Track-A store** (the stated preference, or a summary of the revealing conversation) is decided at Phase 7.
- **D-031: Mem0 / vLLM / HF telemetry is disabled in jobs** (`MEM0_TELEMETRY=False`, `VLLM_NO_USAGE_STATS=1`, `HF_HUB_DISABLE_TELEMETRY=1`, `DO_NOT_TRACK=1`). Compute nodes are also assumed to be offline.
